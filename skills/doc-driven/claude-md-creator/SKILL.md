# CLAUDE.md Creator

## Execution Rules

- CLAUDE.md only does routing, doesn't store detailed info (avoid context rot)
- Detailed project indexes stored separately in docs/ directory, read on demand
- Must contain Constitution (non-negotiable principles)
- Must contain Non-Goals (explicitly not doing)
- Must confirm Non-Goals with user
- Project index files are generated by this skill (during cold start), maintained by the spec-sync skill (during development)
- This skill only scans project structure during cold start and manual "update index"

---

## Cold Start

### Step 1: Parse Requirements

Extract:
- What: What to do
- Why: Why
- Constraints: Constraints
- Non-Goals: Inferred Non-Goals (to be confirmed)

### Step 2: Confirm Non-Goals (Required)

```
Ask user:
"Please confirm which features v1 will NOT do (to prevent AI over-implementation):
□ OAuth third-party login
□ Mobile adaptation
□ Multi-language support
□ Payment gateway integration
□ Data export
□ Other items not to do?"
```

### Step 3: Generate Project Index Files (4)

Scan project structure, generate the following 4 index files:

#### File 1: `docs/project-index.md`

```markdown
# Project File Index

> Must-read before AI development, avoid repeatedly exploring directory structure.

## Entry Points
| Entry Type | File Path | Description |
|------------|-----------|-------------|
| App Entry | src/main.ts | Program startup entry |
| Router Entry | src/router/index.ts | API route registration |
| Config Entry | src/config/index.ts | Config loading |

## Directory Purposes
| Directory | Purpose | Key Files |
|-----------|---------|-----------|
| src/api/ | API interface layer | routes.ts, middleware.ts |
| src/services/ | Business logic layer | auth.service.ts |
| src/models/ | Data models | user.model.ts |
| src/utils/ | Utility functions | logger.ts, validator.ts |
| tests/ | Test files | Organized by module |

## Key Config Files
| File | Purpose |
|------|---------|
| .env.example | Environment variable template |
| tsconfig.json | TypeScript config |
| docker-compose.yml | Local development environment |
```

#### File 2: `docs/dependency-map.md`

```markdown
# Module Dependencies

> Must-read before cross-module modifications, understand impact scope.

## Dependency Direction
api/ → services/ → models/ → utils/
api/ → middleware/ (authentication, logging, error handling)

## Module Responsibility Boundaries
| Module | Responsibility | External Interface |
|--------|----------------|-------------------|
| api/ | Receive requests, parameter validation, return responses | HTTP routes |
| services/ | Business logic orchestration | Service class methods |
| models/ | Data persistence | Model CRUD methods |
| utils/ | General utilities | Pure functions |

## Forbidden Dependency Directions
- models/ → services/ (Data layer does not depend on business layer)
- utils/ → services/ (Utility layer does not depend on business layer)
```

#### File 3: `docs/conventions.md`

```markdown
# Code Conventions

> Conventions not visible in code, must-read before development.

## Naming Conventions
- API routes registered uniformly in src/api/routes.ts
- New Services must be exported in src/services/index.ts
- Database migration file naming: {timestamp}_{action}.ts

## Error Handling Conventions
- Use AppError class uniformly
- Error code format: {module}_{error type}_{sequence number}

## Testing Conventions
- Test files in same directory as source files
- Naming: {filename}.test.ts
- At least 1 test case per acceptance criterion
```

|-----------|-------------------|

- Forbidden to violate Constitution
